## [How Snyk turned an internal support agent into a customer feature](https://www.langchain.com/blog/how-snyk-turned-an-internal-support-agent-into-a-customer-feature)
- **Source:** LangChain blog (Oliver Armstrong) · published 2026-10-08
- **Tags:** #evals #langgraph #tool-permissions
- **Found via:** interests (core: running evals in CI as a release gate; LangGraph; scoped tool permissions)

**Summary:** A customer story about Snyk Assist, a single LangGraph agent that started as an internal support tool and now runs in Slack, a support portal, the web app and an API. A shared agent factory builds the graph from each team's model, tools, prompt, middleware and checkpointer, and conversation state lives in a PostgreSQL checkpointer so sessions can resume across pods. It is hosted by LangChain and every metric is self-reported, but the eval and permission design is concrete enough to borrow.

**Key points:**
- Permissions: typed tools (mostly separate microservices) are attached per request based on what the signed-in user can already see, so the agent can't reach data the user couldn't. The enforcement mechanism itself is not described.
- Release gate: every pull request runs the real agent against LangSmith datasets of real customer questions graded by a second model, plus automated red-teaming for instruction override and secret exfiltration. Merges are blocked by thresholds stored in the repo; the threshold values and grader criteria are not disclosed.
- Online evals: a scheduled job grades every production run on two checks (was it about Snyk, did it answer), which yields a deflection rate. Conversations are also tagged by product area, topic, ecosystem and error type. The LangSmith MCP server lets engineers turn a bad trace into a dataset entry from the IDE.
- Reported numbers: 60,000+ queries, 500+ customer accounts, 85%+ of sessions resolved without a ticket, 250+ cases auto-escalated. "Resolved" and the measurement window are not defined, and no models, latency or cost are given.

## [Introducing Claude Haiku 5.5](https://www.anthropic.com/claude-haiku-5-5)
- **Source:** Anthropic · published 2026-10-07
- **Tags:** #model-release #model-routing #prompt-caching
- **Found via:** interests (core: new model releases; routing between cheap and strong models)

**Summary:** Anthropic's new small model (`claude-haiku-5-5`) has tiered pricing: $0.10 input / $0.50 output per million tokens for prompts up to 100K, and $0.50 / $2.50 above that. Against Haiku 4.5 ($1 / $5) that is 90% cheaper below 100K and 50% cheaper above, and about 75% cheaper on average once a slightly heavier tokenizer is accounted for. It is the first Haiku with an adjustable effort setting (low through max). All benchmark numbers are Anthropic's own.

**Key points:**
- Vendor benchmarks vs Haiku 4.5: OSWorld 2.1 offline subset 72.4% vs 15.7%, Terminal-Bench 4.0 39.2% vs 0.0%, HLE without tools 45.9% vs 10.2%, GDPval-AA v2.1 Elo 1620 vs 735. Sonnet 5.5 stays clearly ahead on Terminal-Bench 4.0 (70.6%).
- Positioning: subagents under Opus 5.5 or Sonnet 5.5, classification, summarization, compaction, database queries, live support and browser use. Anthropic explicitly says not to use it for complex agentic coding.
- Cache pricing: Haiku 5.5 cache reads cost $0.01 per million tokens (under 100K prompts). The same post halves Sonnet 5.5 cache reads from $0.20 to $0.10, which Anthropic estimates cuts Sonnet 5.5 cost on most agentic tasks by about 20%.
- Available via the Claude API and on AWS, Google Cloud and Azure. The post doesn't state the context length. Also announced: monthly API credits for Max and Team plans, and beta computer-use and browser-use support in the Python and TypeScript SDKs.

## [Revamping Skills in Deep Agents](https://www.langchain.com/blog/revamping-skills-in-deep-agents)
- **Source:** LangChain blog (Sydney Runkle) · published 2026-10-07
- **Tags:** #agent-skills #prompt-caching #context-engineering
- **Found via:** interests (core: skills and ways of packaging instructions for agents; prompt caching)

**Summary:** Three additions to how Deep Agents handles Agent Skills (folders with a `SKILL.md` and optional scripts, references and assets, disclosed progressively). Tools can now be bound to a skill, apps can pin skills to a turn, and the skill library can be rescanned mid-thread. Much of the design is about keeping the prompt cache intact. The post is a feature description with no measurements; the running example is LangChain's GTM agent with 50+ skills.

**Key points:**
- Skill-bound tools: list tools under `metadata.include_tools` in the frontmatter and pass them to `SkillsMiddleware(tools=[...])`. They stay hidden, and calling one fails as an unknown tool, until the agent reads the skill. A label can stand in for tool names, and a resolver function maps labels to tools at runtime. That lets you disclose a whole MCP server's tools at once, or gate tools by user identity (the example gives `update_forecast` only to managers).
- Pinned skills: the app parses something like `/meeting-prep` or a UI choice and passes `pinned_skills` to `agent.invoke`. The skill is injected as a tagged message before the next model call, which saves one round trip and avoids the model picking the wrong skill. Deep Agents doesn't parse the user's message itself.
- Reload: passing `skills_metadata=None` rescans skill sources on the next run, so long threads pick up new or changed skills. This rewrites the system prompt and breaks the cache, which the authors argue often doesn't matter for threads that have been idle past cache expiry anyway.
- Cache-safe tool disclosure only works on models that accept new tools mid-conversation (newer Anthropic and OpenAI models get them in a new system message). On other models the tools are appended to the request, which changes the cached prefix.

## [What is Codemode](https://lucumr.pocoo.org/2026/10/6/codemode/)
- **Source:** Armin Ronacher · published 2026-10-06
- **Tags:** #agent-harness #mcp #code-execution
- **Found via:** interests (core: agent harnesses and tool execution; MCP server design)

**Summary:** Ronacher explains Codemode in his Pi harness (shipped with Pi 1.0's MCP support). Instead of making every tool call in the model's context, the agent writes JavaScript that calls tools, runs in a sandbox inside the harness, and returns only what matters. He separates the trusted harness (the "brain") from the execution environment where tools act (the "hands"), and points out that sandboxing the hands, for example with Gondolin, does not sandbox the brain.

**Key points:**
- Implementation: QuickJS compiled to WebAssembly, with no network, no file system, no timers and limited RAM, so its only power is calling more tools. `store()` saves results into the session transcript for later invocations. Pi runs at most four tool executions at once and queues the rest. Codemode is on by default only when MCP is enabled (`"defaultTools": ["+codemode"]` turns it on otherwise).
- Benefits: large outputs stay out of context, scripts can loop and run calls concurrently (a common pattern is probing 5 to 10 items, then scripting the rest), and non-tool APIs such as image generation or classifier models can be exposed without bloating the tool list. Examples include triaging 100 GitHub issues with a classifier and querying the Sentry MCP server in parallel.
- MCP tools are not shown to the model directly. The agent finds them through a tool search inside Codemode. He argues against Cloudflare's approach of putting Codemode inside an MCP server, because it double-escapes JSON, confuses small models and stops inner code from calling outer tools.
- Open problems: durable snapshots of invocations (he suggests workflow engines or Starlark), binary data and images, and weak results with smaller models.
- Requests to MCP server authors: return well-formed JSON and declare `outputSchema`, keep result shapes the same regardless of result count, better large-binary support than pre-signed URLs, and a way to search tools across many servers.

## [From Evidence to Action: How Tool-Using Agents Fail](https://arxiv.org/abs/2610.07753)
- **Source:** arXiv (preprint, not peer reviewed; Princeton, NUS, HKBU and AWS; full text read) · published 2026-10-06
- **Tags:** #evals #agent-failure-modes #agent-reliability
- **Found via:** interests (core: trajectory evals for agents; deterministic tests; agent failure modes)

**Summary:** Introduces SafeActBench, 656 synthetic cases across six domains (customer and policy ops, engineering and infra, legal and financial, research assistance, smart home, healthcare ops). It asks whether each state-changing action was backed by evidence the agent actually gathered first. Cases range from a static allow/block protocol (86 cases) to four interactive ones: investigate-then-don't-act, single action, linear multi-action and dependency-constrained (DAG) workflows. A deterministic evaluator replays trajectories against a provenance-bound evidence ledger instead of using an LLM judge. In a 300-trajectory human audit it falsely accepted 2.0% and falsely rejected 1.3%.

**Key points:**
- Headline gap: on 100 matched single-action cases, models judge a supplied action correctly 95–99% of the time but succeed only 28–52% of the time when they must gather evidence and act themselves. Overall exact case success ranged from 37.7 (GLM-5.2 in ZCode) to 67.2 (Claude Opus 5 in Claude Code), across ten model and harness pairs that also included GPT-5.6 Sol (Codex), DeepSeek-V4-Flash and Qwen3.8-Flash, each also run in Inspect.
- Most failures happen before execution. Agents stop investigating too early (21.7–62.9%) or act before the evidence is complete (37.0–66.9%). Once evidence is complete, single-action success is 93–100% for nine of ten configurations.
- Harness effects depend on the model. Claude, GPT, Qwen and DeepSeek do 2.8–4.7 points better in their own family's harness, while GLM loses 6.8 points in ZCode. Harnesses often shift the type of failure more than the overall rate.
- Withholding a decisive record cuts action rates by 37–45 points, yet agents still act in about half of those episodes. A requester saying "already checked" suppresses action more than the missing evidence does, and generic urgency or warning text has no clear effect.
- Limits: environments are synthetic, the evaluator measures observable support and not what the model relied on internally, the intervention studies are descriptive with wide intervals, and the results are not safety certifications. Resources are at safeact.github.io.

## [EmbeddingGemma 2: an open, lightweight multimodal embedding model](https://blog.google/innovation-and-ai/technology/developers-tools/embeddinggemma-2/)
- **Source:** Google DeepMind, The Keyword blog (Sahil Dua, Henrique Schechter Vera) · published 2026-10-06
- **Tags:** #embeddings #open-weight-models #rag
- **Found via:** interests (core: embedding model choice for RAG; notable small open models)

**Summary:** An Apache 2.0 embedding model built on the Gemma 4 architecture that maps text, code, images, audio, video and interleaved inputs into one vector space. It is modular: about 270M parameters for text-only use, plus an optional vision encoder (about 170M) and audio encoder (about 300M), about 740M in total. Context is 8K tokens, four times the original EmbeddingGemma's, and Matryoshka truncation goes from 768 down to 512, 256 or 128 dimensions. Benchmark claims are Google's own.

**Key points:**
- MTEB Code rises from 68.76 to 78.68. Multilingual text quality is the same as v1. Google claims the best multimodal scores among sub-1B embedders, but the post gives those only as charts; numbers are in the model card.
- On-device footprint (quantized, Pixel 11 Pro): about 191 MB RAM text-only, 567 MB for the full multimodal model. An 8K window holds roughly 5.5 minutes of audio, 29 images or 58 video frames.
- It shares Gemma 4's tokenizer and audio encoder, so the two can run in one local pipeline with less memory, for example offline RAG or local file retrieval.
- Wide tooling support: Hugging Face (`google/embeddinggemma-2`), Kaggle, sentence-transformers, transformers.js/WebGPU, vLLM, llama.cpp (GGUF), SGLang, Ollama, LM Studio, MLX, LiteRT/MediaPipe, Qdrant, and Unsloth for fine-tuning. Model Garden support is still "coming soon".
- Pitched for local code search and retrieval for coding agents, media and audio search, and on-device classification and routing.

## [Can a Cloud-Native Harness Make Agents Reliable Beyond the Desktop?](https://www.latent.space/p/stacklok)
- **Source:** Latent Space (Richard MacManus) · published 2026-10-07
- **Tags:** #cloud-agents #agent-harness #mcp
- **Found via:** exploring (adjacent: cloud-native agent infrastructure)

**Summary:** A feature on Stacklok, founded by Kubernetes co-creators Craig McLuckie and Joe Beda. They argue that coding-agent harnesses are tied to the desktop and that enterprises need them run in the cloud, the way Kubernetes brought control loops to containers. It is founder-driven and high-level, with no benchmarks or internals, so it is useful for framing but not as a design reference.

**Key points:**
- Mecatl, an open-source "cloud-native harness" started in June, keeps the agent loop independent of the client, model provider, state store and execution environment. It moves tool calls and bash execution out of the loop, and moves session state and memory out of local JSONL files.
- Beda says a "lift and shift" into VMs or sandboxes breaks on agent lifecycle and on "quiescing", meaning safely pausing an agent while it waits for a human.
- ToolHive started as a way to run MCP servers in Docker on a desktop and became a Kubernetes gateway, registry and operator for MCP servers, with authentication handled at the gateway.
- Stacklok's AI Gateway (not open source yet) handles access, budgets and provider routing. McLuckie argues that per-task model choice belongs in the harness, which has the context, not in the gateway. Identity, authorization and auditing claims stay generic, with no credential-isolation details.

## [AdvSim2Real: Training Web Agents Against Adaptive Prompt Injection in a Web World Model](https://arxiv.org/abs/2610.08773)
- **Source:** arXiv (preprint, not peer reviewed; MBZUAI, Amazon and MIT; full text read) · published 2026-10-06
- **Tags:** #prompt-injection #web-agents #agent-security
- **Found via:** exploring (adjacent: agent security and real-world failure modes)

**Summary:** Trains a small web agent (Qwen3.5-4B) to resist indirect prompt injection planted in pages. The authors co-evolve three LoRA-adapted roles inside a frozen simulated web (the WebWorld-14B world model, with a frozen Qwen3.8-27B judge). A curriculum proposes tasks the agent solves about half the time. An adaptive attacker picks both the injection text and the step to insert it, and is rewarded only when it flips a success into a failure. The executor trains on clean tasks plus new and old attacks. The paper's point is that fixed injection sets and fixed task sets both stop teaching once they're solved.

**Key points:**
- Benchmark: 150 form-filling tasks across five reasoning strata. Each has protected fields that must not change and forbidden controls (Save draft, Reset all) that must not be clicked.
- Against learned attackers, completion goes from 74.9% clean / 48.1% attacked (base) to 81.3% / 57.5% (final), roughly matching a hosted Qwen3.5-9B. A 24-point gap between clean and attacked runs remains.
- Against a held-out Kimi-K3 attacker, completion rises from 23.0% to 30.7%, but the agent still loses at least 47.7 points against its clean score.
- Real-browser (Chromium) transfer was tested only for capability checkpoints on clean tasks: strict success rose from 25.6% to 44.4%. Robustness gains were measured only inside the simulator, by an LLM judge that sometimes accepts wrong arithmetic. One stratum passed the strict browser check in 0 of 60 episodes while the judge accepted 40–58% of them.
- Cost: one Stage 1 iteration used about 41.5 GPU-hours on two 96 GB RTX 6000 Pro cards. Code, the benchmark and trajectories are released (github.com/Sarim-MBZUAI/advsim2real).
